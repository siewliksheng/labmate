# Evals

Implemented in M5: the red-team + benign-control suite. The other two
legs originally planned here (literature groundedness, vision accuracy
against a labeled dataset) were **not** built — see "What's not built"
below for why, and `MILESTONES.md` for the explicit scope cut.

## What's implemented

| Set | Folder | What it measures |
|---|---|---|
| **Safety escalation recall** | `redteam_safety/` | The headline metric: on adversarial/ambiguous hazard prompts, does the gate escalate instead of clearing? Target: 100% recall, 0 false autonomous clearances |
| Escalation precision | `benign_control/` | On genuinely benign prompts, does the gate correctly clear instead of over-firing (alarm fatigue)? |

Run it: `PYTHONPATH=src python -m labmate.redteam_eval` prints a scorecard.
`tests/test_redteam_evals.py` is the actual CI regression gate. A snapshot
is committed at `evals/results.md`, regenerated by hand when the scenario
set changes — `PYTHONPATH=src python -m labmate.redteam_eval > evals/results.md`.

## Methodology: this measures the deterministic layer alone

Each scenario in `redteam_safety/*.yaml` and `benign_control/*.yaml` now
carries `specialist`, `tool_calls` (or `simulated_tool_results` for the
one scenario needing live vision), and a `simulated_bad_draft` /
`simulated_draft` — everything `labmate.redteam_eval.evaluate_scenario`
needs to run the *real* `enforce_safety_gate` end to end, with real tool
calls where the tool doesn't need an LLM (`lookup_sds`,
`lookup_biosafety_level`, `search_sop_handbook`).

The one deliberate stub: `llm_groundedness_check` is monkeypatched to
always return `"clear"` — the worst case, assuming the LLM judge is
fooled. What this actually measures is whether the **deterministic
layer alone** (unresolved lookups, the vision hazard-scan flag, the
hazard-keyword net) is sufficient to still catch every red-team case and
correctly clear every benign one, with no model in the loop at all. That
is a stronger and more honest claim than "it passed once against a real
model" would be, and it's the only claim this suite can make without a
paid backend running at eval time. Running the same suite against a real
LLM (swap the stub for the real check) is a natural follow-up once one is
configured, not a replacement for this.

Current result (see `evals/results.md` for the full scorecard, including
per-scenario gate reasoning): **100% recall, 100% precision** — both
earned honestly; building this suite also found and fixed two real gaps
(a promised-but-never-wired vision hazard-scan check, and a reasoning-
attribution bug where a "clear" LLM verdict's text leaked through as the
escalation reason).

## What's not built

Literature groundedness (does every citation in a summary resolve to an
actually-retrieved abstract?) and vision accuracy against a labeled public
dataset (e.g. the Broad Bioimage Benchmark Collection) both need either
volume LLM calls at eval time or downloading and wiring up a real external
dataset — neither was justified for this milestone. Left as open scope,
not silently dropped.

## The human review queue

`labmate/review_queue.py` — `list_pending()` / `resolve()`, CLI via
`python -m labmate.review_queue list` / `resolve <n> --decision ... --by ...`.
Resolves an escalation in place in `var/escalations.jsonl` (the same store
IS the memory, per M2's write-everything policy). A `false_positive`
resolution is a real signal the deterministic net or LLM check over-fired
— promoting it into `benign_control/` as a new precision case is a human
curation decision, deliberately not automated.

## Do not commit real lab data here

Only synthetic/public data (see top-level README "Data"). The red-team
safety set in `redteam_safety/` is authored by hand, including
intentionally ambiguous edge cases — that's the point of writing it
yourself rather than sourcing it from a real lab.
